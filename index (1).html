1 RMI / RPC (Remote Invocation & Procedure Dispatch Simulation)

Partial Files: rpc.py, rpc_calls.csv

Concept

A remote procedure call lets a client invoke a procedure that executes in another address space as if it were local. A real system adds a client stub (marshals arguments), a transport, a server skeleton that dispatches by method name, and a reply path. Java RMI is the object-oriented variant of this idea.

How the implementation works

  1. Open rpc_calls.csv and iterate over rows (call_id, client_name, method_name, param_value, timestamp).
  2. Print a [DISPATCH] line.
  3. If method_name == "processData", call the local function processData(value), which returns int(value) * 2.
  4. Print [SERVER EXECUTION] with the parameter and [RETURN] with the result.

Key functions, data structures and formulas

  • processData(value): the only “remote” procedure.
  • Dispatch = one if on method_name; there is no registry or method table.
  • Each CSV row stands for one remote call.

Code excerpt

  • call_id and timestamp are read but never used.

2 Multithreading (Concurrent Processing & Mutex/Lock Synchronization)

Covered Files: multithreading.py, task_1.csv

Concept

Threads run concurrently inside one process and share memory. A mutex (threading.Lock) enforces mutual exclusion so only one thread at a time executes a critical section that touches shared data.

How the implementation works

  1. Create a global lock and a shared list completed_tasks.
  2. Read task_1.csv; start one threading.Thread per row running process_task.
  3. Each thread prints “waiting for lock”, then lock.acquire(), prints “acquired” / “started task”, and releases in a finally block.
  4. Outside the lock it simulates work with time.sleep(burst_ms / 1000).
  5. It re-acquires the lock to append its task_id to completed_tasks.
  6. The main thread join()s every thread and prints the final list.

Key functions, data structures and formulas

  • lock = threading.Lock(); acquire / try / finally release pattern.
  • completed_tasks is the shared state guarded by the lock.
  • Work (sleep) is deliberately outside the critical section.

Code excerpt

3 Lamport’s Logical Clocks (Scalar Timestamps & Total Causal Ordering)

Partial Files: lamport.py, events.csv

Concept

Each process keeps an integer counter. Internal and send events do C = C + 1; on receive, C = max(C, ts_of_message) + 1. If a → b then C(a) < C(b). Ties are broken by process id to obtain a total order.

How the implementation works

  1. Initialise clocks = {"P1": 0, "P2": 0}.
  2. For each row of events.csv: INTERNAL and SEND add 1; RECEIVE uses max(local, int(row["initial_clock"])) + 1.
  3. Append (timestamp, process, event_id) to a list and print each event.
  4. Sort the tuples (timestamp, then process id, then event id) and print it as “Final Causal Order”.

Key functions, data structures and formulas

  • clocks dict, events list of tuples, events.sort().
  • Receive rule is present, but its second operand is the CSV column initial_clock (0 in every row).

Limitations and discrepancies

  • Discrepancy: the receive rule never sees the sender’s timestamp. E2 (SEND) gets 2, yet E3 (its RECEIVE) gets only 1, so the “Final Causal Order” lists E3 before E2, which contradicts happens-before.
  • message_to is never used: sends and receives are not linked. Process names are hard-coded (P1, P2).
  • The total order comes only from sorting; it is not a verified causal order.
  • Illustration (my addition, not in your code): if the send timestamp were carried to the receiver, E3 would become max(0, 2) + 1 = 3.

4 Cristian’s Algorithm (Physical Clock Synchronization & RTT Compensation)

Covered Files: cristian.py, cristian_clocks.csv

Concept

A client asks a time server for the time, measuring send time t0 and receive time t1 on its own clock. It assumes symmetric delay, so the server’s time at receipt ≈ T_server + RTT/2.

How the implementation works

  1. Read each client row: t0_send_ms, t_server_ms, t1_recv_ms.
  2. rtt = t1 − t0.
  3. estimated_time = server_time + rtt/2.
  4. offset = estimated_time − t1 (positive means the client is behind).
  5. adjusted_time = t1 + offset; print all values.

Key functions, data structures and formulas

  • Formulas: RTT = t1 − t0; estimate = T_server + RTT/2; offset = estimate − t1.
  • Each CSV row is an independent client-to-server exchange.

Code excerpt

5 Berkeley’s Algorithm (Physical Clock Averaging & Fault-Tolerant Offset Adjustments)

Partial Files: berkley.py, clocks.csv

Concept

A coordinator collects clock readings from participants, computes their average (discarding faulty or outlying clocks), and tells each participant the offset to apply, rather than imposing a reference time. (The file is spelled berkley.py.)

How the implementation works

  1. Read clocks.csv and keep only rows whose status is ACTIVE (N1–N4; N5 is INACTIVE).
  2. average = sum(clocks) / len(nodes).
  3. For each node: adjustment = average − clock; adjusted_time = clock + adjustment; print.

Key functions, data structures and formulas

  • nodes list of dicts {node_id, clock}.
  • Formula: adjustment_i = avg − clock_i.

6 Vector Clocks (Detecting Concurrency vs. Causal Dependencies)

Covered Files: vector_csv.py, vector_events.csv

Concept

Each process keeps a vector with one slot per process. Local and send events increment the own slot; on receive the vector is merged component-wise by max and the own slot incremented. V1 ≤ V2 (and V1 ≠ V2) means causal precedence; otherwise the events are concurrent.

How the implementation works

  1. Initialise P1, P2, P3 with [0,0,0].
  2. INTERNAL: own slot +1. SEND: own slot +1, then store a copy in messages[(sender, target)].
  3. RECEIVE: fetch messages[(target, process)], take element-wise max, then own slot +1.
  4. Save a copy of the vector per event, then compare every pair with compare(v1, v2).

Key functions, data structures and formulas

  • clocks, events, messages dicts; process_index.
  • compare() returns “Causally Precedes”, “Causally Follows” or “Concurrent”.

7 Ring Algorithm (Leader Election & Token Circulation)

Covered Files: ring.py, ring_nodes_55.csv

Concept

Nodes form a logical ring. An election message circulates, each node passing on the highest id seen; when it has gone round, the highest id is coordinator and is announced around the ring. A token can then circulate around the same ring.

How the implementation works

  1. Load each node’s next_node_id and is_active from ring_nodes_55.csv.
  2. Start from the smallest active id and follow next pointers until a node repeats, collecting only active nodes (inactive N5 is skipped).

8 Bully Algorithm (Leader Election & Coordinator Failure Recovery)

Covered Files: bully.py, bully_cluster_125.csv

Concept

When a node notices the coordinator has failed it sends ELECTION to every higher-id node. Any live higher node replies OK and takes over the election; the live node with the highest id wins and broadcasts COORDINATOR.

How the implementation works

  1. Load node_id, is_alive, is_current_coordinator; report a coordinator that is not alive (Node 4).
  2. Initiator is hard-coded as initiator = 2; abort if it is not alive.
  3. Send ELECTION to every live node with a higher id (3, 5); each “replies” OK.
  4. Elect max(active_nodes) (Node 5) and send COORDINATOR to all live nodes.

Key functions, data structures and formulas

  • nodes list of dicts; active_nodes; higher_nodes; new_leader = max(active_nodes).

9 Dynamic Load Balancing (Round-Robin & Least-Connections Job Scheduling)

Covered Files: load_balancing.py, workload_322.csv, least_connection.py, workload.csv

Concept

Round-robin hands jobs to workers in a fixed cycle regardless of load. Least-connections assigns each job to the worker with the fewest active connections, adapting to current load.

How the implementation works

  1. Round-robin (load_balancing.py): read all jobs; worker = workers[i % 3]; add compute_units to that worker’s load; mark job ASSIGNED.
  2. Least-connections (least_connection.py): start with {W1:3, W2:1, W3:2}; for each job pick min(workers, key=workers.get) and add 1 connection.

Key functions, data structures and formulas

  • i % len(workers) (round-robin).
  • min(workers, key=workers.get) (ties go to the first worker in dict order).

10 MPI Matrix Multiplication (Parallel Row-Partitioning / Scatter-Gather Simulation)

Covered Files: mpi_matrix.py, matrix_184.csv

Concept

In MPI, a master scatters row blocks of A (with B available to all), each rank computes its rows of C = A × B, and the master gathers them. Here C[r][c] = Σ A[r][i]·B[i][c].

How the implementation works

  1. Read matrix A (4×4) from matrix_184.csv; B is a hard-coded 4×4 list.
  2. “Scatter”: start one thread per row running calculate_row.
  3. Each worker computes its row of the product and stores it in results[row_id].
  4. join() all threads (acts as a barrier), then “gather” rows in row_ids order and print the final matrix.

Key functions, data structures and formulas

  • results dict shared among threads (distinct keys, no lock).
  • Triple-loop dot product in calculate_row.

Simulated vs. real distributed execution

Nothing in this project runs across machines. Every script is a single-process simulation: no sockets, no network, no real nodes, and no separate clocks. “Nodes”, “messages” and “clocks” are rows, dict entries and print calls.

  • Real concurrency: multithreading.py and mpi_matrix.py use genuine OS threads within one process (shared memory, CPython GIL).
  • Simulated: RPC, Lamport, Cristian, Berkeley, vector clocks, ring, bully and both schedulers are deterministic CSV-driven calculations.
  • MPI is imitated with threads; mpi4py is not used.
